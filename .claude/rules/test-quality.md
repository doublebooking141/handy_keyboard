# テスト品質保護ルール

## 目的
既存のテストコードを保護し、品質を維持します。

## 禁止事項

### 1. テストの削除・無効化
❌ **禁止**: 既存のテストを削除したり、スキップしたりすること
```c
// NG例
// TEST(suite, test_name) { ... }  // コメントアウトして無効化
```

✅ **許可**: テストが失敗する理由を修正する
```c
// OK例: 実装側のバグを修正してテストをパスさせる
```

### 2. テストの形骸化
❌ **禁止**: テストの検証内容を弱めること
```c
// NG例
// TEST_ASSERT_EQUAL(expected, actual);  // 元の検証
TEST_ASSERT(true);  // 常に成功する検証に変更
```

✅ **許可**: より厳密な検証に変更
```c
// OK例
TEST_ASSERT_EQUAL(expected, actual);
TEST_ASSERT_NOT_NULL(result);  // 追加の検証
```

### 3. テストの意図を歪める変更
❌ **禁止**: テストが検証している内容を変更すること
```c
// NG例: 期待値を実装に合わせて変更
// TEST_ASSERT_EQUAL(100, calculate_total());  // 元のテスト
TEST_ASSERT_EQUAL(50, calculate_total());  // 実装が50を返すように期待値を変更
```

✅ **許可**: テストの意図を保ちながら修正
```c
// OK例: 実装が正しい場合のみ期待値を変更（要レビュー）
TEST_ASSERT_EQUAL(100, calculate_total());  // 実装側を修正してパスさせる
```

## 例外
以下の場合のみ、テストの修正が許可されます:
1. **仕様変更**: 明確な仕様変更がある場合（ドキュメント化必須）
2. **バグ修正**: テスト自体にバグがある場合（理由を明記）
3. **リファクタリング**: テストの可読性向上のみを目的とする場合（検証内容は不変）

## レビュー時の確認事項
- [ ] 既存のテストが削除されていないか
- [ ] テストの検証内容が弱められていないか
- [ ] テストの意図が変更されていないか
- [ ] テスト修正の理由が明確に記載されているか

---

**違反例を発見した場合**: 即座に実装側を修正し、テストをパスさせてください。
